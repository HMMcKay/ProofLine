Documentation / Security

Threat model

Make tampering visible without pretending uncertainty disappeared.

ProofLine is designed against local deletion, truncation, substitution and ambiguous endings. It cannot make an untrusted scene, compromised device or malicious server objectively truthful.

Claims ProofLine can support

  • Exported bytes match signed fragment digests and durable receipts.
  • The displayed start is the first encoded frame in the app-signed chain.
  • A sealed ending reconciles every accepted declared track with a device-signed end manifest.
  • An interrupted ending is the highest contiguous prefix the server accepted before the resume window expired.
  • Verified attestation describes the enrolled signing key and measured app/device state—not the moral reliability of the operator.
  • Signed telemetry, server time and valid TSA tokens can corroborate time and place.

What remains attackable or unknowable

Scene attacks

Staging, coercion, selective framing, an event outside the field of view, a deepfake shown to the lens or screen re-recording.

Device attacks

Rooted phones, malicious camera HAL/firmware, sensor spoofing, stolen unlocked keys and vulnerabilities in a trusted execution environment.

Missing-before-server data

Frames the sensor produced but the app never encoded, or fragments that existed only in an unacknowledged local queue when the device was destroyed.

Custody and legal judgment

A malicious server operator, key theft, case-specific chain of custody, court admissibility and evidentiary weight.

Public-by-design privacy boundary

Irrevocably public warning: ProofLine has no private capture mode, user account or later “unpublish” promise. First launch must communicate this before permission requests.
  • Every capture receives a public permalink and a pseudonymous device grouping.
  • Exact coordinates are retained immediately.
  • While live, public location is reduced to approximately one-kilometer precision.
  • Exact coordinates become public 30 minutes after capture ends.
  • “My devices” is a local convenience list, not authentication or ownership proof.

The delayed location release still creates real safety risk. Operators should consider stalking, retaliation, vulnerable-person and safe-location exposure before enabling a public deployment.

The gateway also validates upload capabilities, route/session identity, signatures, BMFF/container shape, MIME, codec, dimensions, timestamps, sequence and fragment size. Storage unavailability fails closed.

Tombstones

An offline-controlled admin key signs canonical tombstone actions for safety, illegality and abuse response. A tombstone makes playback and raw media downloads return unavailable while preserving:

  • Media hashes and object receipt metadata
  • Server receipts and receipt anchors
  • The offline-admin signature and public reason
  • Prior audit events and report metadata

Tombstoning is not cryptographic deletion and should not be advertised as erasure.

Malicious-server risk

A server that controls object storage and its signing key could withhold new material, refuse uploads or present a partial public view. Receipt exports, optional RFC 3161 anchors, public replication and third-party witnesses reduce—but do not remove—this trust.

Production deployments should move signing to KMS/HSM or PKCS#11, publish server public-key history, retain off-site backups and encourage early independent bundle downloads.

Required language

Use: “high-assurance provenance evidence,” “durably received by this server,” “first encoded frame in the signed chain,” and the exact completeness result.
Do not use: “ironclad,” “court certified,” “guaranteed authentic,” “guaranteed admissible,” or language implying C2PA proves the depicted event objectively happened.
