Deployment and custody

Operate the media plane as evidence infrastructure.

The initial production topology is one HTTPS VPS with isolated internal storage services. Public web delivery stays in Sites; continuous ingest and finalization stay in containers.

Production topology

  • Caddy terminates TLS and is the only trusted reverse proxy.
  • The Rust gateway receives uploads, issues receipts, serves live media/evidence and exposes health/metrics.
  • The Rust worker owns finalization, state expiry, receipt anchors, reports and outbox delivery.
  • PostgreSQL and MinIO/S3 are reachable only on the internal Docker network.
  • Sites binds to MEDIA_CONTROL_URL, MEDIA_PUBLIC_URL and a matching internal secret.

Keys and secrets

Server receipt key

Mount an encrypted PKCS#8 key read-only or inject it from the host secret manager. Publish and retain public-key history.

Offline admin key

Generate and store off-server. Configure only its public SPKI on the gateway.

C2PA credential

The committed certificate is development-only and untrusted. Production needs an operator certificate and chain accepted by the intended trust list.

TLS and internal secret

Use real ACME/TLS, rotate internal HMAC material, and restrict internal routes at the network layer as well as application layer.

Never store private signing keys in D1 or PostgreSQL. The documented upgrade path is an HSM/KMS subprocess signer or PKCS#11.

TLS and proxy policy

Replace the development :80 Caddy listener with the media hostname and operator email, then expose only ports 80 and 443. Do not publish PostgreSQL, MinIO API or MinIO console ports.

Honor forwarding headers only when the connection comes from the configured Caddy proxy. Client-supplied forwarding headers from any other source are untrusted.

Observe and alert

SignalWhy it matters
Readiness failureIngest should not accept work without required storage/database dependencies.
Object-write failureNo receipt may be issued before durable storage succeeds.
Outbox backlogPublic D1 projection may be stale even while authoritative evidence is safe.
Repeated signature rejectionMay indicate attack, client corruption or incompatible protocol code.
Disk/object capacityEvidence availability requires proactive headroom.
Certificate/TSA failureTrust or independent-time corroboration is degraded and must remain visible.
Capture beyond resume windowWorker/job failure may be preventing interruption finalization.

Logs are structured JSON with request IDs. Metrics use Prometheus text format.

Offline tombstone workflow

docker run --rm \
  -v "C:\encrypted\proofline-keys:/keys:ro" \
  --network host \
  --entrypoint proofline-admin proofline-gateway \
  tombstone \
  --gateway https://media.example \
  --capture cap_... \
  --reason "Published safety policy reason" \
  --private-key /keys/admin-private-key.txt

Confirm the exact capture and public reason offline. The action hides media delivery; it does not erase the report or receipt history.

Backup and restore

./scripts/backup.ps1 -OutputDirectory D:\proofline-backups

./scripts/restore.ps1 \
  -BackupDirectory D:\proofline-backups\proofline-YYYYMMDD-HHMMSS \
  -ConfirmRestore RESTORE-PROOFLINE

Back up PostgreSQL, media objects, receipt/C2PA/TLS keys and audit events. Keep an encrypted off-site copy. Test restore on a disconnected clone; restoration stops ingest and replaces the exact MinIO data target.

Release boundaries

Sites: the source remains bound to the existing ProofLine project. Preserve the private deployment as rollback. Replacing it and enabling anonymous public capture requires explicit confirmation immediately before the switch.
GitHub Pages: the documentation workflow publishes only docs/. It does not deploy or change the ProofLine application, Sites access, VPS services or anonymous capture policy.
